# Technical Specification — Task Management Dashboard
## Product Scope
In scope: User registration with email, username, and password; login returning JWT access_token and refresh_token; logout revoking session.In scope: Task CRUD operations (create, read, update, delete) with priorities (low, medium, high, urgent), due dates, categories, tags, status (todo, in_progress, done), reminders, and assignment to other users.In scope: Task search by title/description keyword using ILIKE matching on both columns; filtering by priority, status, category_id, assignee_id; pagination with page/page_size parameters.In scope: Category management — users can create categories (unique name per user), list their own categories, and delete them. Tasks reference categories via foreign key with ON DELETE SET NULL.In scope: Analytics dashboard showing total tasks, tasks by priority, tasks by status, and overdue count via GET /api/v1/analytics/tasks.In scope: Responsive web interface with desktop sidebar navigation and mobile bottom tab bar; task cards with color-coded priorities; analytics summary cards and charts.In scope: Swagger/OpenAPI documentation available at /docs (HTML) and /openapi.json (JSON).In scope: RESTful API with consistent error responses, Pydantic validation, and proper HTTP status codes.In scope: Task reminders stored as an array of ISO 8601 datetime strings on the task record.In scope: Docker containerization as required by the brief's technical constraints. The product ships a Dockerfile (python:3.12-slim base, installs dependencies from requirements.txt, copies application code, runs uvicorn) and docker-compose.yml (api service on port 8000 depending on db service running PostgreSQL on port 5432 with pgdata volume).In scope: Team collaboration is implemented through direct task assignment to individual users — any registered user can be assigned tasks by other users who own those tasks. There is no separate team entity, team creation endpoint, team membership model, or team management page; the brief's 'team collaboration' requirement and acceptance criterion 'Team collaboration features function properly' are satisfied when a user can create a task and assign it to another registered user, and that assigned user can see, update, and complete their assigned tasks.Deferred: Reminder trigger mechanism and notification channels.Deferred: Complex analytics visualizations beyond summary counts and simple charts.Deferred: Standalone tag management features separate from task records.Deferred: WebSocket real-time updates.Deferred: File attachments on tasks.Deferred: Time tracking on tasks.

## Component Boundaries
- Backend (task-management-dashboard/task_management_dashboard/main.py): FastAPI application providing RESTful API endpoints for authentication, tasks, categories, and analytics. Handles all business logic, database access via SQLAlchemy ORM, request validation via Pydantic v2, and error handling. Runs as a standalone Python process served by uvicorn on configurable PORT.
- Frontend (task-management-dashboard/src/App.tsx): React application built with Vite, providing the user interface. Communicates with the backend via fetch() calls to /api/v1/ endpoints. All routing handled client-side using React Router. Token storage uses sessionStorage for access_token and refresh_token; on page load the app attempts to refresh the session using the stored refresh_token before rendering protected routes. During active use, if any API call returns 401 (unauthorized), the frontend intercepts the response, uses the stored refresh_token to POST /api/v1/auth/refresh for a new access_token, replaces the old token in sessionStorage, and automatically retries the failed request with the new token. If the refresh itself fails (refresh_token expired or revoked), the user is redirected to the login page.
- Database: PostgreSQL when DATABASE_URL is set; file-based SQLite (under DATA_DIR) when DATABASE_URL is unset. Schema managed via Alembic migrations for both PostgreSQL and SQLite.
- Authentication flow: Client sends credentials to POST /api/v1/auth/register or POST /api/v1/auth/login; backend returns access_token (15-min expiry) and refresh_token (7-day expiry); all subsequent API requests include access_token in Authorization header as Bearer token; refresh mechanism via POST /api/v1/auth/refresh exchanges refresh_token for new access_token; logout via POST /api/v1/auth/logout revokes the refresh token and the current access token's jti.
- Configuration: All settings read from environment variables at startup (PORT, DATA_DIR, DATABASE_URL, JWT_SECRET_KEY, JWT_ALGORITHM, ACCESS_TOKEN_EXPIRE_MINUTES, REFRESH_TOKEN_EXPIRE_DAYS, CORS_ORIGINS). No configuration files shipped with the product. JWT_SECRET_KEY reads from the JWT_SECRET_KEY environment variable if set; otherwise a deterministic key is generated at first start and persisted under DATA_DIR/jwt_secret.key so it survives restarts.
- Access token revocation: A revoked_tokens table stores jti values of blacklisted access tokens. On logout the current access token's jti is inserted into this table. During token validation the jti is checked against revoked_tokens; if found the token is rejected with 401. On refresh (POST /api/v1/auth/refresh), the old access token's jti is also inserted into revoked_tokens, immediately invalidating it.
- Containers (task-management-dashboard/Dockerfile and task-management-dashboard/docker-compose.yml): Docker containerization as required by the brief. Dockerfile uses python:3.12-slim base, WORKDIR /app, copies requirements.txt then installs dependencies, copies application code, EXPOSE 8000, CMD runs uvicorn. docker-compose.yml defines two services: 'api' (builds from Dockerfile, maps port 8000:8000, environment DATABASE_URL=postgresql://user:pass@db:5432/taskdb JWT_SECRET_KEY CORS_ORIGINS depends_on db condition service_healthy) and 'db' (image postgres:16, environment POSTGRES_USER/POSTGRES_PASSWORD/POSTGRES_DB, maps port 5432:5432, volume pgdata:/var/lib/postgresql/data, healthcheck using pg_isready).
- Acceptance testing orchestration: The script task-management-dashboard/scripts/serve-acceptance.mjs (harness-managed) first runs Vite build to produce the frontend bundle, then starts uvicorn serving the FastAPI backend on PORT. The frontend's fetch() calls reach the backend because both serve from the same origin during acceptance tests; the acceptance suite waits until GET /api/health returns 200 before running any tests.

## Domain Model
- User: id (UUID PK), email (VARCHAR(255) UNIQUE NOT NULL), username (VARCHAR(100) NOT NULL), password_hash (VARCHAR(255) NOT NULL), is_active (BOOLEAN NOT NULL DEFAULT true), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), updated_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()). A user can own tasks, be assigned to tasks, and own categories.
- RefreshToken: id (UUID PK), user_id (UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE), token_hash (VARCHAR(255) UNIQUE NOT NULL), expires_at (TIMESTAMPTZ NOT NULL), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), revoked (BOOLEAN NOT NULL DEFAULT false). A refresh token is tied to exactly one user and can be revoked independently. Index on (user_id, expires_at).
- RevokedToken: id (UUID PK), jti (VARCHAR(255) NOT NULL), expires_at (TIMESTAMPTZ NOT NULL), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()). Stores the jti claim of access tokens that have been actively revoked (e.g., on logout or refresh). A token whose jti appears here is rejected even if not yet expired.
- Task: id (UUID PK), title (VARCHAR(255) NOT NULL), description (TEXT), priority (VARCHAR(10) NOT NULL CHECK IN ('low', 'medium', 'high', 'urgent')), due_date (TIMESTAMPTZ), status (VARCHAR(20) NOT NULL DEFAULT 'todo' CHECK IN ('todo', 'in_progress', 'done')), category_id (UUID REFERENCES categories(id) ON DELETE SET NULL), assignee_id (UUID REFERENCES users(id)), creator_id (UUID NOT NULL REFERENCES users(id)), version (INTEGER NOT NULL DEFAULT 0), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), updated_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), tags (SQLAlchemy JSON NOT NULL DEFAULT JSON('[]')) - array of string tags, reminders (SQLAlchemy JSON NOT NULL DEFAULT JSON('[]')) - array of ISO 8601 datetime strings for reminder trigger times. Index on (assignee_id, status), (creator_id, status), priority.
- Category: id (UUID PK), name (VARCHAR(100) NOT NULL), user_id (UUID NOT NULL REFERENCES users(id)), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()). CONSTRAINT unique_category_per_user UNIQUE (name, user_id). Each user owns their categories; name must be unique within a single user's category list. A category can have many tasks; a task belongs to at most one category.

## API and Event Contracts
- POST /api/v1/auth/register: Request body {email: string (RFC 5321, max 255 chars), username: string (min 3 chars, max 100 chars), password: string (min 8 chars)} → 201 with {id: uuid, email: string, username: string} or 409 on duplicate email or 422 on validation failure. Rate limited to 5 req/min by IP.
- POST /api/v1/auth/login: Request body {email: string, password: string} → 200 with {access_token: string, refresh_token: string, token_type: 'bearer'} or 401 on invalid credentials or 422 on validation failure. Rate limited to 10 req/min by IP.
