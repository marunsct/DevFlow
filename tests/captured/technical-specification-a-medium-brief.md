# Technical Specification — Task Management Dashboard
## Product Scope
## What this release coversA task management dashboard with two parts: a React frontend SPA and a FastAPI backend API.**User management**: Registration, login, and logout with JWT access tokens (15-minute expiry) and refresh tokens (7-day expiry). Users authenticate before accessing any protected resource.**Task management**: Full CRUD for tasks. Each task has a title (3-200 characters), optional description, priority (low, medium, high, urgent — default medium), optional due date, status (pending, in_progress, completed, cancelled — default pending), and an owner (the authenticated user). Tasks can be assigned to other registered users via the user_tasks relationship table. Tasks support categories (array of strings, max 100 chars each) and tags (array of strings, max 100 chars each), stored as ARRAY<VARCHAR(100)> columns.**Search and filter**: GET /api/tasks accepts query parameters q (text search on title and description), priority (filter by single priority value), status (filter by single status value), due_date_start (ISO 8601 date), and due_date_end (ISO 8601 date). The frontend provides a text input for search, dropdown selects for priority and status, and optional date range inputs. Results are filtered based on these parameters.**Reminders**: Each task can have multiple reminders. A reminder has a due_at timestamp (ISO 8601 datetime), optional note text, and a triggered flag. Reminders are stored in a separate reminders table. The GET /api/reminders endpoint returns two arrays: upcoming (due_at > now and triggered=false) and due (due_at within the last 5 minutes and triggered=false). Reminders are evaluated on-demand — no background scheduler. The client is responsible for notifying the user.**Analytics**: A dashboard page showing task statistics — total tasks, counts by priority, counts by status, overdue task count, and tasks_by_owner (dict mapping owner user_id strings to task counts). Analytics queries are team-wide (all tasks, not just the current user's).**API documentation**: Swagger/OpenAPI docs served at /docs, auto-generated by FastAPI.**Error handling**: All endpoints return structured JSON error responses with a correlation ID. Validation errors return 422, authentication errors return 401, not-found returns 404, forbidden returns 403, and rate-limit violations return 429 with a Retry-After header.**Responsive design**: Desktop layout (≥768px) with fixed left sidebar navigation; mobile layout (<768px) with hamburger menu and slide-over drawer.## What this release defers- Team collaboration features beyond basic task assignment and reminders (comments, notifications, activity feeds)- Docker containerization files are written (Dockerfile, docker-compose.yml) but not built or tested in this environment — the files are complete and syntactically valid; only the build/test step is deferred- Rate limiting on endpoints other than registration and login- Read replicas or database sharding- Social/OAuth login providers

## Component Boundaries
- Frontend (task-management-dashboard/src/): React SPA built with Vite. Contains App.tsx (routing and layout), components/ (reusable UI components), hooks/ (custom hooks for auth and API calls), types/ (TypeScript interfaces), and utils/ (helper functions). Communicates with the backend via fetch('/api/...').
- Backend API (task-management-dashboard/task_management_dashboard/): FastAPI application with route modules (auth.py, tasks.py, analytics.py, reminders.py), data models (models.py for SQLAlchemy ORM), schemas (schemas.py for Pydantic request/response models), authentication (auth.py for JWT logic), database (database.py for session management), and main.py (app factory and middleware).
- Database (PostgreSQL): File-based SQLite in development (DATA_DIR/default), PostgreSQL in production (DATABASE_URL). Schema managed by Alembic migrations. Tables: users, tasks, user_tasks, refresh_tokens, reminders.
- Acceptance tests (task-management-dashboard/acceptance/): Playwright tests (*.spec.js) that start the backend service and frontend, then exercise the full stack through a headless browser.
- Unit tests (task-management-dashboard/tests/): Vitest tests for frontend components (*.test.tsx) and pytest tests for backend logic (*.py).
- Configuration: Environment variables (PORT, DATA_DIR, DATABASE_URL, JWT_SECRET, JWT_ALGORITHM, ACCESS_TOKEN_EXPIRE_MINUTES, REFRESH_TOKEN_EXPIRE_DAYS, CORS_ORIGINS) read at process startup.

## Domain Model
- User: A registered account. Fields — id (BIGSERIAL primary key), username (VARCHAR(50) UNIQUE NOT NULL, CHECK length >= 3), email (VARCHAR(255) UNIQUE NOT NULL, valid email format), password_hash (VARCHAR(255) NOT NULL, bcrypt hash), full_name (VARCHAR(100), nullable), is_active (BOOLEAN NOT NULL DEFAULT TRUE), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), last_login_at (TIMESTAMPTZ, nullable), last_logout_at (TIMESTAMPTZ, nullable). A user owns tasks and can be assigned tasks.
- Task: A work item. Fields — id (BIGSERIAL primary key), title (VARCHAR(200) NOT NULL, CHECK length >= 3), description (TEXT, nullable), priority (VARCHAR(10) NOT NULL DEFAULT 'medium', CHECK value IN ('low', 'medium', 'high', 'urgent')), due_date (DATE, nullable), status (VARCHAR(20) NOT NULL DEFAULT 'pending', CHECK value IN ('pending', 'in_progress', 'completed', 'cancelled')), owner_id (BIGINT NOT NULL, FK to users.id ON DELETE RESTRICT), categories (ARRAY<VARCHAR(100)>, nullable), tags (ARRAY<VARCHAR(100)>, nullable), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), updated_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), completed_at (TIMESTAMPTZ, nullable). A task has one owner and zero or more assignees.
- UserTask: A many-to-many relationship between users and tasks (for assignment). Fields — id (BIGSERIAL primary key), task_id (BIGINT NOT NULL, FK to tasks.id ON DELETE RESTRICT), user_id (BIGINT NOT NULL, FK to users.id ON DELETE RESTRICT), assigned_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), assigned_by (BIGINT, FK to users.id ON DELETE SET NULL), note (TEXT, nullable). UNIQUE(task_id, user_id) prevents duplicate assignments.
- RefreshToken: A token used to obtain new access tokens. Fields — id (BIGSERIAL primary key), user_id (BIGINT NOT NULL, FK to users.id ON DELETE CASCADE), token_hash (VARCHAR(255) NOT NULL, SHA-256 hex digest of the raw token), expires_at (TIMESTAMPTZ NOT NULL), revoked (BOOLEAN NOT NULL DEFAULT FALSE), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()).
- Reminder: A notification trigger for a task. Fields — id (BIGSERIAL primary key), task_id (BIGINT NOT NULL, FK to tasks.id ON DELETE CASCADE), due_at (TIMESTAMPTZ NOT NULL), note (TEXT, nullable), triggered (BOOLEAN NOT NULL DEFAULT FALSE). A reminder belongs to one task.
- Priority enum: 'low', 'medium', 'high', 'urgent'. Stored as VARCHAR with CHECK constraint.
- Status enum: 'pending', 'in_progress', 'completed', 'cancelled'. Stored as VARCHAR with CHECK constraint.
- Analytics: Computed aggregates — total_tasks (COUNT(*)), by_priority (COUNT(*) GROUP BY priority), by_status (COUNT(*) GROUP BY status), overdue_tasks (COUNT(*) WHERE due_date < CURRENT_DATE AND status NOT IN ('completed', 'cancelled')), tasks_by_owner (COUNT(*) GROUP BY owner_id).
- ARRAY column compatibility: The Task model's categories and tags columns use SQLAlchemy's ARRAY type. In PostgreSQL, these are stored as native ARRAY<VARCHAR(100)>. In SQLite (used for development and testing), SQLAlchemy maps ARRAY columns to JSON type, storing values as JSON arrays. The ORM layer handles this transparently — reads and writes work identically in both databases. No application code needs to distinguish between the two backends.

## API and Event Contracts
- POST /api/register — Register a new user. Request body: {username: string (3-50 chars, non-whitespace pattern ^\S+$), email: string (valid email format), password: string (min 8 chars)}. Response 201: {id: int, username: string, email: string, created_at: string (ISO 8601)}. Response 409: {error: Username or email already exists, correlation_id: string}. Response 422: {error: Validation error, correlation_id: string, details: array}. Rate-limited: 5 requests per IP per 15 minutes, returns 429 with Retry-After header.
- POST /api/login — Authenticate and receive tokens. Request body: {email: string, password: string}. Response 200: {access_token: string (JWT, HS256 signed, 15-minute expiry), token_type: string ("bearer")}. Sets refresh_token as HTTP-only Secure cookie with SameSite=Strict. Response 401: {error: Invalid credentials, correlation_id: string}. Rate-limited: 5 requests per IP per 15 minutes.
- POST /api/logout — Invalidate the current session. Requires Authorization: Bearer <access_token>. No request body. Response 200: {message: Logged out successfully}. Response 401: invalid/expired/missing token.
- POST /api/refresh — Obtain a new access token using the refresh token cookie. No request body. Response 200: {access_token: string (JWT, HS256 signed, 15-minute expiry), token_type: string ("bearer")}. Response 401: {error: Invalid or expired refresh token, correlation_id: string}.
- GET /api/health — Health check. No auth required. Response 200: {status: string ("healthy")}.
- GET /api/tasks — List the authenticated user's tasks (owned + assigned). Query params: q (optional, text search on title and description), priority (optional, filter by single priority value), status (optional, filter by single status value), due_date_start (optional, ISO 8601 date), due_date_end (optional, ISO 8601 date), page (optional, int >= 1, default 1), page_size (optional, int 1-100, default 20). Response 200: {tasks: array, total: int, page: int, page_size: int}. Each task: {id: int, title: string, description: string|null, priority: string, due_date: string (ISO 8601 date)|null, status: string, owner: {id: int, username: string}, assignees: array<{id: int, username: string}>, categories: array of string|null, tags: array of string|null, created_at: string (ISO 8601), updated_at: string (ISO 8601), completed_at: string (ISO 8601)|null}. Response 401: unauthenticated.
- POST /api/tasks — Create a new task. Requires auth. Request body: {title: string (3-200 chars), description: string|null, priority: string (default medium), due_date: string (ISO 8601 date)|null, status: string (default pending), categories: array of string|null, tags: array of string|null, assignees: array of {user_id: int, note: string|null}|null}. Response 201: {id: int, title: string, description: string|null, priority: string, due_date: string|null, status: pending, owner: {id: int, username: string}, assignees: array, categories: array|null, tags: array|null, created_at: string, updated_at: string, completed_at: null}. Response 401: unauthenticated. Response 422: validation error.
- GET /api/tasks/{task_id} — Get a single task by ID. Requires auth (owner or assignee). Response 200: task object as above. Response 401: unauthenticated. Response 404: task not found or user not authorized.
- PUT /api/tasks/{task_id} — Update a task. Requires auth (owner only). Request body (all fields optional): {title: string (3-200 chars)|null, description: string|null, priority: string|low|medium|high|urgent|null, due_date: string (ISO 8601 date)|null, status: string|pending|in_progress|completed|cancelled|null, categories: array of string|null, tags: array of string|null}. Response 200: updated task object. Response 401: unauthenticated. Response 403: not the owner. Response 404: not found. Response 422: validation error.
- DELETE /api/tasks/{task_id} — Delete a task. Requires auth (owner only). Response 200: {message: Task deleted}. Response 401: unauthenticated. Response 403: not the owner. Response 404: not found.
- POST /api/tasks/{task_id}/assign — Assign a task to another user. Requires auth (owner only). Request body: {user_id: int, note: string|null}. Response 200: {message: Task assigned, user_id: int}. Response 401: unauthenticated. Response 403: not the owner. Response 404: task or user not found. Response 422: validation error.
- DELETE /api/tasks/{task_id}/assignments/{user_id} — Remove an assignment. Requires auth (owner only). Response 200: {message: Assignment removed}. Response 401: unauthenticated. Response 403: not the owner. Response 404: not found.
- POST /api/reminders — Create a reminder for a task. Requires auth (owner only). Request body: {task_id: int, due_at: string (ISO 8601 datetime), note: string|null}. Response 201: {id: int, task_id: int, due_at: string, note: string|null, triggered: false}. Response 401: unauthenticated. Response 403: not the task owner. Response 404: task not found.
- GET /api/reminders — Get reminders for tasks owned by or assigned to the user. Requires auth. Response 200: {upcoming: array of {id: int, task_id: int, due_at: string, note: string|null, triggered: bool}, due: array of {id: int, task_id: int, due_at: string, note: string|null, triggered: bool}}. Response 401: unauthenticated.
- DELETE /api/reminders/{reminder_id} — Delete a reminder. Requires auth (owner of the associated task). Response 200: {message: Reminder deleted}. Response 401: unauthenticated. Response 403: not the task owner. Response 404: reminder not found.
- GET /api/analytics — Get task statistics. Requires auth. Response 200: {total_tasks: int, by_priority: {low: int, medium: int, high: int, urgent: int}, by_status: {pending: int, in_progress: int, completed: int, cancelled: int}, overdue_tasks: int, tasks_by_owner: {user_id_string: int}}. Response 401: unauthenticated.
- GET /docs — Swagger UI documentation. No auth required. Response 200: HTML.
- GET /openapi.json — OpenAPI JSON schema. No auth required. Response 200: JSON object.

## Data Flows
- Registration: Client POSTs /api/register with username, email, password. Backend validates input via Pydantic schema, checks for duplicate username/email in database, hashes password with bcrypt (rounds=12), inserts User record, commits once, returns 201 with user data.
- Login: Client POSTs /api/login with email, password. Backend validates input, looks up user by email, verifies password with bcrypt.checkpw, updates last_login_at = NOW(), generates JWT access token (15-min expiry, sub=str(user.id), iat=NOW()), generates refresh token as raw 32-byte hex string, hashes refresh token with SHA-256, inserts RefreshToken record with token_hash, commits once, constructs response body {access_token: <access_token>, token_type: "bearer"} from the access token, sets refresh_token as HTTP-only Secure cookie with SameSite=Strict and Secure flag, returns {access_token, token_type} in JSON body.
- Token refresh: Client POSTs /api/refresh. Backend reads raw refresh token from cookie, hashes it with SHA-256, looks up token_hash in refresh_tokens table where revoked=FALSE and expires_at > NOW(), validates the record is not expired and not revoked, gets user_id from the RefreshToken record, generates new JWT access token (15-min expiry, sub=str(user_id), iat=NOW()), revokes old refresh token (sets revoked=TRUE), creates new refresh token (raw 32-byte hex string), hashes new refresh token with SHA-256, inserts new RefreshToken record, commits once, returns {access_token, token_type} in JSON body.
- Logout: Client POSTs /api/logout with Authorization header. Backend decodes access token (catches JWTError → 401), gets user_id from sub claim, looks up user, sets last_logout_at = NOW(), revokes all refresh tokens for user (sets revoked=TRUE), commits once, returns 200.
- Task creation: Authenticated user POSTs /api/tasks with title, optional fields. Backend validates input, creates Task record with owner_id=current_user.id, creates UserTask records for any assignees, commits once, returns 201 with full task object including owner and assignees.
- Task listing: Authenticated user GETs /api/tasks with optional query parameters (q, priority, status, due_date_start, due_date_end). Backend queries tasks where owner_id=current_user.id OR user_id=current_user.id in user_tasks. Applies q parameter as LIKE '%q%' search on title and description columns. Applies priority and status filters if provided. Applies due_date_start and due_date_end range filters if provided (due_date >= due_date_start AND due_date <= due_date_end). Paginates. Returns task array with metadata.
- Task update: Owner PUTs /api/tasks/{id} with fields to update. Backend verifies ownership (owner_id=current_user.id). Raises 403 if not owner. Applies updates, sets updated_at=NOW(). If status is updated to 'completed', sets completed_at=NOW(). If status is updated away from 'completed', sets completed_at=NULL. Commits once, returns updated task.
- Task deletion: Owner DELETEs /api/tasks/{id}. Backend verifies ownership. Raises 403 if not owner. Deletes task and associated UserTask and Reminder records. Commits once, returns 200.
- Task assignment: Owner POSTs /api/tasks/{task_id}/assign with user_id. Backend verifies ownership. Raises 403 if not owner. Raises 404 if user not found. Inserts UserTask record. Commits once, returns 200.
- Reminder creation: Task owner POSTs /api/reminders with task_id, due_at, optional note. Backend verifies ownership. Raises 403 if not owner. Raises 404 if task not found. Inserts Reminder record. Commits once, returns 201.
- Reminder listing: Authenticated user GETs /api/reminders. Backend queries reminders for tasks owned by or assigned to the user where triggered=false. Splits into upcoming (due_at > now) and due (due_at within last 5 minutes of now). Returns both arrays.
- Reminder deletion: Task owner DELETEs /api/reminders/{id}. Backend verifies ownership via associated task. Raises 403 if not owner. Deletes reminder. Commits once, returns 200.
- Analytics: Authenticated user GETs /api/analytics. Backend runs team-wide SQL aggregations (COUNT(*) for total_tasks, COUNT(*) GROUP BY priority for by_priority, COUNT(*) GROUP BY status for by_status, COUNT(*) WHERE due_date < CURRENT_DATE AND status NOT IN ('completed', 'cancelled') for overdue_tasks, COUNT(*) GROUP BY owner_id for tasks_by_owner), returns computed statistics as JSON.
- Database access: All database operations use SQLAlchemy async session via FastAPI Depends(get_db, scope=function). Sessions are created per-request. All writes commit within the route handler before returning (not in teardown). Every write is wrapped in an explicit transaction that rolls back on exception.
- Access token validation: get_current_user decodes the JWT access token, verifies the HS256 signature, checks exp claim, then looks up the User record and verifies that last_logout_at is NULL or last_logout_at <= token.iat. If last_logout_at > iat, raises HTTPException(401, "Token revoked").

## Security and Privacy
- JWT authentication: Access tokens are short-lived (15 minutes), contain sub=str(user.id), iat (issued at), and exp claims, signed with HS256 algorithm using JWT_SECRET from environment. Refresh tokens are long-lived (7 days), stored as raw random strings (32-byte hex), hashed with SHA-256 before storage, stored in HTTP-only Secure cookies with SameSite=Strict. Token rotation on refresh prevents reuse attacks.
- Access token invalidation: JWT access tokens include an iat (issued at) claim. The User record has a last_logout_at column (TIMESTAMPTZ, nullable). The get_current_user dependency checks that user.last_logout_at is NULL or user.last_logout_at <= token.iat. If last_logout_at > iat, the token is rejected with HTTP 401. On logout, the route sets last_logout_at = NOW() before returning, ensuring immediate invalidation of the access token.
- Password hashing: bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12)) for storage, bcrypt.checkpw(password.encode(), stored_hash) for verification.
- Rate limiting: Registration and login endpoints limited to 5 requests per IP address per 15-minute sliding window. Implemented via in-memory rate limiter keyed by client IP. Returns 429 with Retry-After header (seconds until window resets) when limit exceeded.
- CORS: FastAPI CORSMiddleware configured with CORS_ORIGINS from environment (comma-separated origins, parsed by splitting on commas and stripping whitespace). Only GET, POST, PUT, DELETE, OPTIONS methods allowed. Only Content-Type and Authorization headers allowed. credentials=True for cookie support.
- Input validation: Every request body validated against Pydantic models with Field() constraints. Invalid input returns 422 with field-level error details. PostgreSQL CHECK constraints provide second-line defense.
- Transaction safety: All database writes wrapped in explicit transactions. Session.commit() called only on success, session.rollback() on any exception. Commit happens within the route handler before return to avoid FastAPI 0.118 teardown timing issue.
- Error responses: All errors return JSON with {error: string, correlation_id: string}. Correlation ID is a UUID generated per request. Stack traces, SQL errors, and internal details never exposed to client.
- Database secrets: DATABASE_URL, JWT_SECRET read from environment variables (os.environ) at startup. Never hardcoded.
- Data persistence: Data stored under DATA_DIR (default 'data/') for file-based SQLite. Never committed to version control via .gitignore.
- Shutdown: Signal handler for SIGTERM closes database connection pool within 30 seconds. Prevents data loss during deployment or crashes.

## Reliability and Observability
- Health check: GET /api/health returns 200 {status: healthy} with no authentication.
- Structured logging: Python logging module with JSON-formatted entries for request ID, method, path, status code, and response time. Request ID generated per request (UUID).
- Database connection pool: SQLAlchemy create_async_engine with pool_size=5, max_overflow=10, pool_timeout=30, pool_recycle=1800. Connection pool closed on shutdown.
- Error tracking: All unhandled exceptions caught by FastAPI exception handler, logged with stack trace (server-side only), and returned to client as generic error with correlation_id.
- API documentation: FastAPI auto-generates OpenAPI schema at /openapi.json and Swagger UI at /docs.
- Graceful shutdown: FastAPI shutdown handler registered at app startup. Closes database connection pool with 30-second timeout.
- Migration safety: Alembic migrations applied before service starts. Each migration has up() and down() scripts.

## Testing
- Unit tests (frontend): Vitest runner. Files: task-management-dashboard/tests/*.test.tsx. Tests React components in isolation using React Testing Library. Run with: npm test.
- Unit tests (backend): pytest runner. Files: task-management-dashboard/tests/test_*.py. Tests pure logic functions against plain Python objects. Run with: python -m pytest tests/ -c pytest.ini.

- Test AC-4 (Set priorities): Playwright test that POSTs tasks with each of four priority values (low, medium, high, urgent) in separate requests, GETs each task asserting priority matches submitted value.
- Test AC-5 (Categories and tags): Playwright test that creates a task with categories and tags, GETs the task asserting they are returned, PUTs the task with updated values asserting changes persist.
- Test AC-6 (Reminders): Playwright test that creates a reminder for a task, GETs reminders asserting the reminder appears in upcoming, asserts that due reminders are returned in the due array.
- Test AC-8 (Secure registration, login, logout): Playwright test that registers user, logs in to obtain JWT token, calls logout endpoint, then accesses protected endpoint with same token asserting 401 response.
- Test AC-9 (Task CRUD operations): Playwright test that creates task via POST with title, priority, due date, GETs task asserting all fields returned correctly, PUTs task with modified values asserting response reflects updates, DELETEs task asserting subsequent GET returns 404.
- Test AC-11 (Analytics dashboard): Playwright test that creates at least five tasks with varied priorities and due dates via the API, logs in as a registered user, navigates to the analytics dashboard page, and asserts that the rendered page contains numeric statistics reflecting the created tasks.
- Test AC-12 (API documentation): Playwright test that sends GET /docs asserting 200 response with HTML containing 'Swagger' or 'OpenAPI'.
- Test AC-13 (Proper error handling): Playwright tests that POST /register with empty body, POST /login with missing fields, POST /tasks without authorization header, PUT /tasks/{id} with invalid JSON, asserting each returns a 4xx status code with an error message in the response body.
- Test AC-14 (Responsive design): Playwright test that loads the application page, asserts that the main container element is visible and rendered, and asserts that the page contains a valid viewport meta tag.

- Test isolation: Each test uses unique usernames and emails to avoid collisions. No shared mutable state between tests. Database reset between acceptance tests: each acceptance test runs in its own Playwright worker process with a separate SQLite file. The acceptance suite's playwright.config.js assigns a unique DATA_DIR per worker (e.g., 'data/worker-0/', 'data/worker-1/') via the workerId property, so each worker gets a fresh database file. The serve-acceptance.mjs script passes DATA_DIR through environment variables. This ensures complete isolation — no state leaks between tests.

## Deployment
- Development: Run backend with 'python -m uvicorn task_management_dashboard.main:app --reload --host 127.0.0.1 --port 8000'. Run frontend dev server with 'npx vite'. Apply migrations with 'alembic upgrade head'.
- Acceptance test environment: scripts/serve-acceptance.mjs builds the frontend with Vite and starts the backend with uvicorn. Acceptance tests connect to http://localhost:<PORT>/api/... and the frontend at http://localhost:<PORT>/.
- Production: DATABASE_URL points to PostgreSQL server. JWT_SECRET is a strong random string. CORS_ORIGINS lists allowed frontend origins. Data directory for file persistence is mounted as a volume. Port configured via PORT environment variable.
- Docker: docker-compose.yml defines services for backend (uvicorn + FastAPI), frontend (nginx serving built React app), and PostgreSQL. Multi-stage Dockerfile for backend (python:3.12-slim base, install dependencies, copy code). Dockerfile for frontend (node:20-alpine base, build React app, nginx serving static files). Files are written; only the build/test step is deferred in this environment.
- Migrations: database.py calls alembic.command.upgrade(engine, 'head') after engine creation to apply any pending migrations. For PostgreSQL, this runs once at startup. For SQLite file databases, migrations are applied on every start (idempotent). Migration files live in task-management-dashboard/alembic/. The alembic.ini configuration file is included in the project root.
- Environment variables: PORT (default 8000), DATA_DIR (default 'data/'), DATABASE_URL (default 'sqlite+aiosqlite:///./data/tasks.db'), JWT_SECRET (default 'dev-secret-change-in-production'), JWT_ALGORITHM (default 'HS256'), ACCESS_TOKEN_EXPIRE_MINUTES (default 15), REFRESH_TOKEN_EXPIRE_DAYS (default 7), CORS_ORIGINS (default 'http://localhost:5173').
- Start script: task-management-dashboard/start.sh starts the backend service. The acceptance suite uses scripts/serve-acceptance.mjs which builds the frontend and starts the backend.

## Acceptance Criteria
- AC-1: User registration and authentication — A new user can register with a unique username (3-50 chars, non-whitespace), email, and password (min 8 chars). After registration, the user can log in with email and password. Login returns an access_token (JWT string) and sets a refresh_token cookie.
- AC-2: Create, read, update, delete tasks — An authenticated user can POST a task with title and priority. GET /api/tasks returns the created task. PUT /api/tasks/{id} updates the task fields. DELETE /api/tasks/{id} removes the task. Subsequent GET returns 404.
- AC-3: Assign tasks to team members — A user can POST /api/tasks/{id}/assign with another user's ID. The task's GET response includes the assignee. A non-owner attempting to assign receives 403 Forbidden.
- AC-4: Set priorities — Tasks can be created with any of the four priority values (low, medium, high, urgent). GET returns the correct priority. An invalid priority returns 422.
- AC-5: Categories and tags — Tasks can be created with categories and tags arrays. GET returns them. PUT updates them. Each value is validated as max 100 chars.
- AC-6: Reminders — A task owner can create a reminder with a due_at timestamp. GET /api/reminders returns upcoming reminders (due_at > now) and due reminders (due_at within last 5 minutes). A non-owner attempting to create a reminder receives 403 Forbidden.
- AC-7: Task update sets completed_at — When a task's status is updated to 'completed', the response includes a non-null completed_at timestamp. When status is updated away from 'completed', completed_at is null.
- AC-8: Users can register, login, and logout securely — After logout, the same access token cannot access protected endpoints (returns 401).
- AC-9: Task CRUD operations work correctly — Creating a task with title, priority, and due date returns all fields. Updating fields reflects in the GET response. Deleting removes the task (404 on subsequent GET).
- AC-10: Token refresh returns only access_token — POST /api/refresh returns a JSON body with access_token and token_type only, no refresh_token field.

## Function Contracts
- login_user: File: task-management-dashboard/task_management_dashboard/auth.py. Signature: login_user(email: str, password: str, db: AsyncSession) -> tuple[User, str, str]. Steps: 1. Query User by email. 2. If not found or bcrypt.checkpw(password.encode(), user.password_hash) is False, raise HTTPException(401, "Invalid credentials"). 3. Generate JWT access token with sub=str(user.id), exp=15min, iat=NOW(). 4. Generate raw refresh token as 32-byte hex string using secrets.token_hex(32). 5. Return (user, access_token, refresh_token_raw). Returns: tuple of (User ORM object, access_token JWT string, refresh_token_raw 32-byte hex string). Raises: HTTPException(401, "Invalid credentials") on invalid credentials.
- refresh_access_token: File: task-management-dashboard/task_management_dashboard/auth.py. Signature: refresh_access_token(raw_token: str, db: AsyncSession) -> tuple[str, str]. Steps: 1. Hash raw_token with SHA-256 (hashlib.sha256(raw_token.encode()).hexdigest()). 2. Query RefreshToken by token_hash where revoked=FALSE and expires_at > NOW(). 3. If not found, raise HTTPException(401, "Invalid or expired refresh token"). 4. Get user_id from the RefreshToken record. 5. Generate new JWT access token with sub=str(user_id), exp=15min, iat=NOW(). 6. Mark old refresh token as revoked (set revoked=TRUE). 7. Generate new raw refresh token as 32-byte hex string using secrets.token_hex(32). 8. Hash new refresh token with SHA-256. 9. Insert new RefreshToken record with token_hash, user_id, expires_at=NOW()+7days. 10. Return (new_access_token, new_raw_token). Returns: tuple of (new_access_token JWT string, new_raw_token 32-byte hex string). Raises: HTTPException(401, "Invalid or expired refresh token") if token not found, expired, or revoked.
- logout_user: File: task-management-dashboard/task_management_dashboard/auth.py. Signature: logout_user(user_id: int, db: AsyncSession) -> None. Steps: 1. Query User by id. 2. Set user.last_logout_at = NOW(). 3. Query all RefreshToken records for this user where revoked=FALSE. 4. Set all found refresh tokens to revoked=TRUE. 5. Commit the session. Returns: None. Raises: None.
- get_current_user: File: task-management-dashboard/task_management_dashboard/auth.py. Signature: get_current_user(authorization: str = Header(None), db: AsyncSession = Depends(get_db)) -> User. Steps: 1. If authorization is None or does not start with "Bearer ", raise HTTPException(401, "Not authenticated"). 2. Extract JWT token from "Bearer <token>". 3. Decode token with jwt.decode() using HS256 and JWT_SECRET, verify=True. 4. Extract sub claim and convert to int. 5. Query User by id. 6. If user is not active, raise HTTPException(401, "Account inactive"). 7. If user.last_logout_at is not None and user.last_logout_at > token.iat, raise HTTPException(401, "Token revoked"). 8. Return user. Returns: User ORM object. Raises: HTTPException(401) on invalid/missing/revoked token or inactive account.
- create_task: File: task-management-dashboard/task_management_dashboard/routes/tasks.py. Signature: create_task(body: TaskCreate, current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> TaskResponse. Steps: 1. Create Task record with title, description, priority, due_date, status, owner_id=current_user.id. 2. For each assignee in body.assignees, create UserTask record. 3. Commit the session. 4. Return TaskResponse from the created task. Returns: TaskResponse. Raises: HTTPException(422) on validation error.
- list_tasks: File: task-management-dashboard/task_management_dashboard/routes/tasks.py. Signature: list_tasks(q: str|None, priority: str|None, status: str|None, due_date_start: str|None, due_date_end: str|None, page: int, page_size: int, current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> dict. Steps: 1. Query tasks where owner_id=current_user.id OR exists in user_tasks for current_user. 2. Apply q filter as LIKE '%q%' on title and description. 3. Apply priority filter if provided. 4. Apply status filter if provided. 5. Apply due_date range filter if provided. 6. Paginate results. 7. Return {tasks: array, total: int, page: int, page_size: int}. Returns: dict with tasks array and pagination metadata.
- get_task: File: task-management-dashboard/task_management_dashboard/routes/tasks.py. Signature: get_task(task_id: int, current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> TaskResponse. Steps: 1. Query Task by id. 2. If not found, raise HTTPException(404, "Task not found"). 3. Check if current_user is owner or assignee. 4. If not, raise HTTPException(403, "Not authorized"). 5. Return TaskResponse. Returns: TaskResponse. Raises: HTTPException(404) if not found, HTTPException(403) if not authorized.
- update_task: File: task-management-dashboard/task_management_dashboard/routes/tasks.py. Signature: update_task(task_id: int, body: TaskUpdate, current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> TaskResponse. Steps: 1. Query Task by id. 2. If not found, raise HTTPException(404, "Task not found"). 3. If owner_id != current_user.id, raise HTTPException(403, "Not authorized"). 4. Apply non-null fields from body to task. 5. If status changed to 'completed', set completed_at=NOW(). If status changed away from 'completed', set completed_at=NULL. 6. Set updated_at=NOW(). 7. Commit the session. 8. Return TaskResponse. Returns: TaskResponse. Raises: HTTPException(404) if not found, HTTPException(403) if not owner.
- delete_task: File: task-management-dashboard/task_management_dashboard/routes/tasks.py. Signature: delete_task(task_id: int, current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> dict. Steps: 1. Query Task by id. 2. If not found, raise HTTPException(404, "Task not found"). 3. If owner_id != current_user.id, raise HTTPException(403, "Not authorized"). 4. Delete associated UserTask records. 5. Delete associated Reminder records. 6. Delete Task. 7. Commit the session. 8. Return {message: "Task deleted"}. Returns: dict. Raises: HTTPException(404) if not found, HTTPException(403) if not owner.
- assign_task: File: task-management-dashboard/task_management_dashboard/routes/tasks.py. Signature: assign_task(task_id: int, body: dict, current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> dict. Steps: 1. Query Task by id. 2. If not found, raise HTTPException(404, "Task not found"). 3. If owner_id != current_user.id, raise HTTPException(403, "Not authorized"). 4. Query User by body.user_id. 5. If not found, raise HTTPException(404, "User not found"). 6. Insert UserTask record. 7. Commit the session. 8. Return {message: "Task assigned", user_id: body.user_id}. Returns: dict. Raises: HTTPException(404) if task or user not found, HTTPException(403) if not owner.
- get_analytics: File: task-management-dashboard/task_management_dashboard/routes/analytics.py. Signature: get_analytics(current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)) -> AnalyticsResponse. Steps: 1. Run SQL aggregation for total_tasks (COUNT(*)), by_priority (COUNT(*) GROUP BY priority), by_status (COUNT(*) GROUP BY status), overdue_tasks (COUNT(*) WHERE due_date < CURRENT_DATE AND status NOT IN ('completed', 'cancelled')), tasks_by_owner (COUNT(*) GROUP BY owner_id). 2. Return AnalyticsResponse. Returns: AnalyticsResponse.

## Error Catalogue
- 400 Bad Request: Returned when a request body cannot be parsed as JSON. Body: {error: Invalid JSON, correlation_id: string}.
- 401 Unauthorized: Returned when authentication is missing, expired, or invalid. Body: {error: string, correlation_id: string}. Specific messages: 'Invalid credentials' (login), 'Token expired' (logout with expired token), 'Invalid token' (logout with malformed token), 'Invalid or expired refresh token' (refresh), 'Not authenticated' (other endpoints).
- 403 Forbidden: Returned when the authenticated user is not the owner of a resource. Body: {error: Not authorized, correlation_id: string}. Applied to task update, task delete, task assignment, reminder create, reminder delete.
- 404 Not Found: Returned when a requested resource does not exist. Body: {error: Not found, correlation_id: string}. Specific messages: 'Task not found', 'User not found', 'Reminder not found'.
- 409 Conflict: Returned when a registration attempt uses an existing username or email. Body: {error: Username or email already exists, correlation_id: string}.
- 422 Unprocessable Entity: Returned when request body validation fails. Body: {error: Validation error, correlation_id: string, details: array of {field: str, message: str}}.
- 429 Too Many Requests: Returned when rate limit is exceeded on registration or login. Body: {error: Too many requests, correlation_id: string}. Headers: Retry-After: int (seconds).
- 500 Internal Server Error: Returned for unhandled exceptions. Body: {error: Internal server error, correlation_id: string}. Stack trace logged server-side only.

### ADR-03 — JWT with refresh token rotation
**Context:**
The brief requires JWT tokens with refresh mechanism. The security specialist recommends refresh token rotation.

**Decision:**
Access tokens: 15-minute expiry, HS256 signed, sub=str(user.id). Refresh tokens: 7-day expiry, SHA-256 hashed before storage, stored in HTTP-only Secure cookies with SameSite=Strict. Each refresh rotates the token (revokes old, creates new).

**Rationale:**
Short-lived access tokens minimize exposure window. Refresh token rotation prevents token reuse attacks. HTTP-only cookies prevent XSS theft. SHA-256 hashing ensures raw tokens are never stored.

**Trade-offs:**
- Token rotation adds one extra database write per refresh.
- HTTP-only cookies require CSRF protection on the refresh endpoint (mitigated by SameSite=Strict and origin validation).

**Consequences:**
- Refresh tokens table with token_hash column.
- Cookie-based token storage in frontend.
- Logout must revoke all active refresh tokens for the user.

**Validation evidence:**
Stack facts: python-jose 3.5.0 (2025-05-28) supports HS256. PyJWT 2.10+ requires sub to be a string.
Evidence relied on (stack facts, read 2026-11-25): JWT - package: pypi `jwt`; current release (date): 1.4.0 (2025-06-23); support: not tracked by endoflife.date; open advisories: none known; toolchain fit: fits python 3.12.16 (needs >=3.9); pack: no

### ADR-04 — bcrypt for password hashing
**Context:**
The security specialist recommends bcrypt with rounds=12. passlib 1.7.4 is incompatible with bcrypt 5.

**Decision:**
Use bcrypt directly: bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12)) for hashing and bcrypt.checkpw(password.encode(), stored_hash) for verification. Pin bcrypt<5 in dependencies.

**Rationale:**
bcrypt is the industry standard for password hashing. Rounds=12 provides good security (approximately 250ms per hash on modern hardware). Direct use avoids passlib's incompatibility with bcrypt 5.

**Trade-offs:**
- Direct bcrypt usage means slightly more code than using passlib's high-level API.
- bcrypt<5 pin limits access to future bcrypt improvements.

**Consequences:**
- Password hashes stored as VARCHAR(255) in database.
- No dependency on passlib for hashing (passlib can still be used for other utilities).
- bcrypt package required in dependencies.

**Validation evidence:**
Stack facts: passlib 1.9.5 (2026-11-23). The framework constraints note passlib 1.7.4 fails with bcrypt 5; using bcrypt 4.x resolves this.

### ADR-06 — VARCHAR with CHECK constraints instead of PostgreSQL ENUM
**Context:**
The database specialist recommends PostgreSQL ENUM types for priority and status. However, SQLite (used in development) does not support ENUM types.

**Decision:**
Use VARCHAR columns with CHECK constraints for priority and status fields. This provides the same validation at the database level while remaining compatible with both SQLite and PostgreSQL.

**Rationale:**
CHECK constraints work identically in SQLite and PostgreSQL, ensuring consistent validation across environments. This avoids the need for dialect-specific migration scripts.

**Trade-offs:**
- PostgreSQL ENUM types would provide slightly better type safety at the database level.
- Slightly more storage (VARCHAR vs internal ENUM representation), but negligible for this schema.

**Consequences:**
- priority column: VARCHAR(10) NOT NULL DEFAULT 'medium' CHECK (priority IN ('low', 'medium', 'high', 'urgent')).
- status column: VARCHAR(20) NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'in_progress', 'completed', 'cancelled')).
- Alembic migrations use VARCHAR with CHECK for both SQLite and PostgreSQL.

**Validation evidence:**
SQLAlchemy documentation: VARCHAR with CHECK constraint is the standard cross-dialect approach for enum-like constraints.

### ADR-07 — Commit within route handler, not in teardown
**Context:**
FastAPI 0.118+ runs teardown code after the response is sent. A commit in teardown could land after the client reads the database.

**Decision:**
All database commits happen within the route handler, before returning the response. The database session dependency uses scope='function' to ensure each request gets a fresh session.

**Rationale:**
This ensures the database state is consistent when the client receives the response. TestClient (used in unit tests) waits for teardown, but the running service does not, so committing in teardown would cause the service to fail while tests pass.

**Trade-offs:**
- Slightly more code in each route handler to handle commit/rollback explicitly.
- Error handling must be more careful to ensure rollback on failure.

**Consequences:**
- get_db dependency: session = AsyncSession(engine); yield session; session.close().
- Route handlers: try: session.commit() except: session.rollback(); raise.

**Validation evidence:**
FastAPI documentation: 'Since FastAPI 0.118 the code after yield in a dependency runs once the response has been sent.'

### ADR-13 — JWT sub claim as string for PyJWT 2.10+ compatibility
**Context:**
PyJWT 2.10 and later refuses a token whose sub claim is not a string (InvalidSubjectError on decode).

**Decision:**
Convert user.id to string on encode: jwt.encode({'sub': str(user.id), 'exp': ...}). Convert back to int on decode: int(jwt.decode(token)['sub']).

**Rationale:**
PyJWT 2.10+ strictly enforces sub as a string type. Using str(user.id) satisfies this requirement while preserving the numeric user ID in the token.

**Trade-offs:**
- Slightly larger token payload (string representation of integer).
- All JWT-reading code must convert sub back to int.

**Consequences:**
- auth.py encode_token function: jwt.encode({'sub': str(user.id), ...}).
- auth.py decode_token function: int(decoded['sub']).
- All route handlers receiving user.id from JWT decode it as int.

**Validation evidence:**
Framework constraints: 'PyJWT 2.10 and later refuses a token whose sub claim is not a string (InvalidSubjectError on decode).' Stack facts: JWT 1.4.0 (2025-06-23).
