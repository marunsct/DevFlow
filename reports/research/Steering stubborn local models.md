# Make the harness enforce what prompts cannot

A stubborn small open-weight model is steered mainly by **mechanisms that take the wrong move away**, and much less by wording that asks it to behave. Ranked by how certain the effect is and how many of the five failure modes each covers, the playbook runs like this. First, put a hard cap on every generation and cut reasoning from the client side. Second, force structure only through the llama.cpp paths that really enforce it: the string `tool_choice: "required"` with a reduced tool set, or `response_format` with no tools. Third, intercept repeated or refused calls deterministically and hand back the ready-to-run corrected call. Fourth, keep refused attempts and stale file dumps out of the context the model conditions on. Fifth, make the `<think>` token impossible to sample when you prefill reasoning. Prompt changes (one binding rule restated last, positive phrasing, a compact per-model prompt) and sampling changes (temperature near 0.6 rather than near-greedy, DRY with a long window) come after these. Fine-tuning on the harness's own refusal logs is the most durable fix and also the most expensive. The stakes are concrete. For LFM2.5 on llama.cpp, three of the five failures are **legal under the decoder configuration the harness likely sends today**. Under `tool_choice: "auto"` the tool grammar is lazy, so a prose answer is allowed. The LFM2.5 tool grammar does not enforce array types, enums or `required`. A named `tool_choice` object is **silently downgraded to `"auto"`**. Everything below can be implemented as data in a per-model profile whose values are chosen by a fixed probe battery. Server flags such as `--reasoning-budget` and KV-cache type belong to the model owner, so the harness-owned levers are per-request fields and client-side control.

## The ranked playbook at a glance

The ranking weighs three things: certainty of effect (a decoder guarantee beats a measured average, which beats an inference), how many failure modes the item covers, and implementation cost. "Mechanism-certain" means llama.cpp source code guarantees the behaviour. The size of the effect on this model is still unmeasured.

| Rank | Technique | Failures addressed | Evidence | Generic implementation (profile-driven) |
|---|---|---|---|---|

Stream, count reasoning tokens, abort at `profile.reasoning_cap`, then continue with a closed-think prefill (rank 5) |
| 2 | Decoder-enforced structure: string `required` plus a reduced tool set; `response_format` with no tools for schema answers; extraction pass for prose | (3), part of (1) | Mechanism-certain (llama.cpp code); strong evidence that constraints do not hurt accuracy | `profile.tool_choice_mode`, `profile.structured_path`; never send the named `tool_choice` object to llama.cpp |

## Reasoning spirals of 100k tokens are loops, and a cap costs little

The overthinking literature agrees that most long-reasoning tokens add little. Chen et al. found that o1-like models spend heavy compute on trivial inputs (QwQ-32B-Preview produced 13 solutions to "2+3"), and that such patterns "contribute minimally to improving accuracy" ([arXiv 2412.21187](https://arxiv.org/html/2412.21187v2)). Training-free early exit (DEER) **cut chain-of-thought length by 19.1-80.1% while improving accuracy by 0.3-5.0 points** across 11 reasoning models ([arXiv 2504.15895](https://arxiv.org/pdf/2504.15895)). Dynasor observed "answer stabilization", the point after which extra compute stops changing the answer, and reported up to 50% compute savings with no accuracy drop ([arXiv 2412.20993](https://arxiv.org/abs/2412.20993)). ThinkPrune halved DeepSeek-R1-Distill-1.5B's AIME24 traces from about 15,484 to 8,301 tokens for a drop of 29.4% to 29.0% ([arXiv 2504.01296](https://arxiv.org/html/2504.01296v1)). Qwen3's budget curves rise smoothly from 2k up to 32k tokens ([arXiv 2505.09388](https://arxiv.org/html/2505.09388v1)). An 80k-144k-token reply sits far outside every curve published, and none of these papers measured cutting a degenerate trace, so the claim that "a cap near 8k-16k loses almost nothing" is an extrapolation. It is a safe one, because a spiral that never terminates scores zero anyway.

The cap has to come from the harness. llama.cpp's `n_predict` defaults to **-1, meaning infinite** ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)), so every request needs an explicit `max_tokens`. The server has a real budget sampler, `--reasoning-budget N` with `--reasoning-budget-message`. When the budget runs out it forces the end-of-think tokens by setting every other logit to -inf, through an IDLE→COUNTING→FORCING→DONE state machine ([reasoning-budget.h mirror](https://huggingface.co/datasets/echodict/llama.cpp/blob/main/common/reasoning-budget.h)). It is a **server flag, not a documented per-request field**, so changing it means changing the owner's server configuration. It also has a regression history. Later think blocks were unbudgeted until the re-arm fix #22323 ([commit](https://app.semanticdiff.com/gh/ggerganov/llama.cpp/commit/52e5f0a5c180248ffae41fe74060d21a07651a93)), and one report says builds after 2026-04-10 default to an effectively unlimited budget, with silent hangs ([forge issue #54](https://github.com/antoinezambelli/forge/issues/54)). The harness-owned equivalent is a client-side cut. Stream the reply, count reasoning tokens, abort at `profile.reasoning_cap`, and send one continuation request whose assistant prefill is the truncated reasoning, a single short "answer now" sentence and a closed `</think>`. Qwen3's official cut sentence is a good template: "Considering the limited time by the user, I have to give the solution based on the thinking directly now." ([arXiv 2505.09388](https://arxiv.org/html/2505.09388v1)). Keep that message to one line. In benchmarks of llama.cpp's draft budget PR, an intro message and soft warnings made cuts *less* reliable, because "the model, once told it has a budget, treats the injected cut sentence as part of its own plan and continues past it"; the intro was later dropped ([PR #25961](https://github.com/ggml-org/llama.cpp/pull/25961)). So the budget should never be announced in the prompt. Enforce it silently.

Sampling is the second lever for spirals, but only for the verbatim kind. The LFM2.5 card recommends **temperature 0.1**, yet its benchmarks ran mostly at 0.6 ([LFM2.5 card](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B)). Qwen3's card warns that greedy decoding "can lead to performance degradation and endless repetitions" ([Qwen3-8B card](https://huggingface.co/Qwen/Qwen3-8B)). A near-greedy temperature on an always-thinking model is a loop risk factor, so the profile should treat temperature as a measured parameter starting near 0.6. Check which value is actually deployed, because the brief and the live card disagree. DRY is the one anti-repetition sampler with good evidence. It cut verbatim loop steps by **47% (SER@4 0.124→0.065) on 1.5-7B models** and left Llama-3-70B's MMLU and GSM8k within 0.1 point. A classic repetition penalty cost 3.7 GSM8k points, and presence and frequency penalties "barely moved" loops ([arXiv 2608.22761](https://www.alphaxiv.org/abs/2608.22761.md)). DRY is a per-request llama.cpp field but is off by default, and its default window `dry_penalty_last_n=64` ([README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)) is far too short for a 100k-token trace. Start from multiplier 0.8, base 1.75, allowed length 2-4, a window of 1024 or more, and extra sequence breakers for code punctuation. Without breakers, false-positive penalties on structural tokens rose from 1.2% to 28.4% in the same study. Two caveats bound this lever. DRY was never tested on think traces or long code, and it "addresses only surface-form continuation loops". The "wait, let me re-check" semantic spiral falls to the cap, not to DRY.

## Prefilled reasoning re-opens `<think>` because nothing forbids it

Failure (5) and the client-side cut are linked: the cut works only if the continuation does not start a fresh think block. LFM2.5 is "a pure reasoning model that always thinks before it answers", and its template opens every assistant turn with `<think>` ([LFM2.5 card](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B)). llama.cpp treats a final assistant message as a prefix to continue ([README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). A prefill that carries reasoning in any other shape is therefore a state the model never saw in training, and re-opening `<think>` is its trained reflex. No source measured this failure, so the cause is inferred from the template. The remedy, however, is mechanism-certain. `logit_bias` with the value `false` "prevents [a token] from being produced" ([README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). The profile should store the think-open token id, found once through `/tokenize`, and send `logit_bias: [[id, false]]` on every continuation request, with `"<think>"` in `stop` as a backstop in case the tag tokenizes into several pieces. The prefill itself should be a *closed* block: the reasoning, the one-line answer-now sentence, then `</think>`. The budget state machine sets its initial state from the prefill. An unclosed `<think>` starts in COUNTING, and with a budget of 0 or less it is promoted straight to FORCING ([reasoning-budget.h](https://huggingface.co/datasets/echodict/llama.cpp/blob/main/common/reasoning-budget.h)). So on servers where the owner runs a budget, a closed prefill avoids a second forced cut. The other option is to send no reasoning back at all. Qwen3's guidance is that history "should only include the final output part" ([Qwen3-8B card](https://huggingface.co/Qwen/Qwen3-8B)), and Sinha et al. suggest stripping prior thinking may explain why thinking models resist self-conditioning ([arXiv 2509.09677](https://arxiv.org/html/2509.09677v3)). Carrying a two-line summary of the truncated reasoning into a user-role "answer now with one call" turn is the safer variant when the ban cannot be verified. One question remains open: whether, under a non-lazy tool grammar, the forced `</think>` and the prefill compose cleanly. The probe battery should test that.

## llama.cpp enforces less structure than the OpenAI API implies

The prose-instead-of-tool failure is partly self-inflicted. llama.cpp builds a lazy grammar under `tool_choice: "auto"`, and for LFM2.5 the trigger is the literal `<|tool_call_start|>`. Until the model emits it, **nothing is constrained, and pure prose is a legal answer** ([lfm2.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/parsers/lfm2.cpp)). The grammar becomes non-lazy only under `response_format` or `tool_choice == "required"`. The server reads `tool_choice` **as a string only**. The OpenAI named-function object fails the type check, gets logged as "Wrong type supplied for parameter", and quietly becomes `"auto"` ([server-common.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-common.cpp)). That matters for LangChain users. `ToolStrategy` and `with_structured_output(method="function_calling")` send the named form and therefore get auto semantics, held up only by `handle_errors` retries ([LangChain structured output](https://docs.langchain.com/oss/python/langchain/structured-output#error-handling-strategies)). To force a specific tool on llama.cpp, send **only that tool** with the string `"required"`. Even then LFM2.5's Python-style tool grammar enforces only the tool name, argument names, and whether a value is a quoted string. Argument order is free, repeats are allowed, and `required`, `enum`, `pattern`, `minItems` and array typing are not enforced ([chat-peg-parser.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/chat-peg-parser.cpp)). That is why a string arrives where a list is wanted, and why a whole shell line fits into one argument. JSON-style handlers (Hermes/Qwen templates) do compile the full parameter schema, so the profile must record which handler the template selects. `GET /props` exposes the template ([function-calling.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)), and the probe battery should check whether a schema violation is even possible.

Full schema enforcement exists only on the `response_format: {"type":"json_schema", ...}` path **with no tools**. With tools present, the response schema is ignored ([lfm2.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/parsers/lfm2.cpp)), and a custom `grammar` with tools is rejected outright ([server-common.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-common.cpp)). The GBNF converter has limits that shape schema design. Unsupported features "are skipped silently", `prefixItems` is broken, nested `$ref` is broken, patterns must be anchored `^…$`, and required properties are always emitted first ([grammars/README.md](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)). A reasoning field must therefore be required, or it will follow the answer. For a structured answer, the profile should name the `ProviderStrategy`/`response_format` path. For a prose reply where structure was required, the cheapest recovery is a second extraction request: the prose as context, no tools, `response_format` set to the schema. That beats re-prompting "use the tool". Fear of hurting the model is not a reason to hold back. On JSONSchemaBench, every constrained engine was at or above the unconstrained baseline: llama.cpp grammar scored 82.4 against 80.1 on GSM8K for Llama-3.1-8B. Grammar decoding did double the time per token (29.98 ms against 15.4 ms) ([arXiv 2501.10868](https://arxiv.org/html/2501.10868)). The "format restrictions hurt reasoning" result mostly disappears with matched prompts and a reason-first field ([dottxt](https://blog.dottxt.ai/say-what-you-mean.html)), and CRANE shows that free reasoning followed by a constrained answer preserves accuracy ([arXiv 2502.09061](https://arxiv.org/abs/2502.09061)). LFM2.5's free `<think>` block before the constrained part already follows that pattern. The real risk is a constrained but wrong value, "a validly-parsable function call - not a high-quality one" ([vLLM docs](https://docs.vllm.ai/en/latest/features/tool_calling.html)). So constraint must be paired with post-hoc validation. Follow OpenHands' converter: coerce `int()` and `json.loads` for arrays, and reject unknown or missing parameters and non-enum values with messages that name the parameter and the expected shape ([fn_call_converter.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/llm/mixins/fn_call_converter.py)). Schemas should stay flat, with every field required and an enum for every closed set. To make "program plus args in one string" impossible, split it into a `program` field with an anchored no-whitespace pattern and an `args` array. That pattern is enforced only on the full-grammar path; elsewhere the harness must check it after parsing.

## One failed call drops recovery odds from 90% to 57%, so the first refusal must carry the fix

SWE-agent's trajectory analysis gives the stakes for failure (1). An edit attempt eventually succeeds 90.5% of the time, but **only 57.2% after one failure**, and cascading failed edits caused 23.4% of failures ([SWE-agent paper](https://arxiv.org/abs/2405.15793)). Every surveyed harness answers repeats the same way: detect, nudge once, then stop or hand off. OpenHands' `StuckDetector` nudges after **3 identical errors** with the message "Repeating the exact same call again will not work — review the error message and either correct the arguments or try a different approach", and halts at 4 ([stuck_detector.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py); [types.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/types.py)). Gemini CLI hashes name plus arguments, catches cycles of length 1-5 at 5 repeats, sends one feedback turn and aborts on the second detection ([loopDetectionService.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/loopDetectionService.ts)). Roo Code refuses to execute the call at its limit of 3 ([ToolRepetitionDetector.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/core/tools/ToolRepetitionDetector.ts)). None of these thresholds has been ablated, and the exact-match keys have a weakness: OpenHands compares the `thought` text too, so a model that rewords its reasoning or changes `head -n 20` to `head -n 40` resets the streak. The generic fix is a **normalized key**, for example the tool, the refusal class and the leading program, so "the same refusal N times" counts whatever the surface variation.

How the refusal is written matters more than any counter. Anthropic's guidance is to return "specific and actionable improvements, rather than opaque error codes" and to "give examples of correctly formatted tool inputs" ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)). Huang et al. found that self-correction without external feedback does not reliably help, and that verifiable external feedback does ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)). That argues against Gemini-style "take a step back" nudges and for refusals that do the model's work for it. For a line like `cd x && cat y | head`, the pattern is regular enough for a deterministic rewriter to parse and turn into the equivalent call to a dedicated read tool, with path, offset and limit resolved. The refusal then returns that exact call ready to copy, or the harness simply runs it. SWE-agent's ablations support purpose-built tools over shell: removing the edit command cut success from 18.0% to 10.3%, and a bounded 100-line viewer beat full-file display ([SWE-agent paper](https://arxiv.org/abs/2405.15793)). Offering fewer tools per step also helps edge models ([Less is More](https://arxiv.org/abs/2411.15399)). This rewriter has never been compared with plain refusal text, so its benefit is an inference, but it is the cheapest experiment on the list.

The strongest result in this area concerns what the model sees afterwards. Sinha et al. show "self-conditioning": a model's error rate rises when its context holds its own earlier mistakes, scaling *increases* this for non-thinking models, and a sliding window that drops old turns "significantly improves performance" ([arXiv 2509.09677](https://arxiv.org/abs/2509.09677)). Ten refused shell lines left in the transcript are an injected-error history. SWE-agent's `forward_with_handling` requeries up to 3 times inside a *temporary* history, and "if the model is able to correct itself, the records of the mistakes will not be part of the history" ([agents.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/agents.py)). The profile should select one of three history policies, ordered by how much they hide: drop corrected refusals entirely, collapse them into one line ("3 refused shell lines omitted; use read_file"), or keep them. When the streak reaches the reset threshold, Magentic-One's response applies: re-plan and "force all agents to clear their contexts", restarting from a summarized state. Removing its progress ledgers cost about 31% on GAIA ([arXiv 2411.04468](https://arxiv.org/abs/2411.04468)). One more inference deserves a probe. Instruction-hierarchy training teaches models to discount lower-privileged text such as tool output ([arXiv 2404.13208](https://arxiv.org/abs/2404.13208)), so a refusal delivered only as a tool result may carry less weight than the same text in a user-role turn. The profile should make the refusal's role a measured setting.

Re-reading files already in context (failure 4) yields to the same tools. SWE-agent's collapsed old observations beat full history, 18.0% against 15.0% ([SWE-agent paper](https://arxiv.org/abs/2405.15793)), and its history processors mark stale file views as "Outdated window with N lines omitted" ([history_processors.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/history_processors.py)). LFM2.5 leads Qwen3.6-35B-A3B on IFEval but trails it on SWE-Bench Verified, 51.0 against 66.2 ([LFM2.5 card](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B)). That profile suggests weak long-horizon recall rather than weak instruction parsing, which fits a hybrid design with only 10 attention layers out of 40, though this is speculative. The practical design is a context ledger. A read of an unchanged file returns "already in context at message N, unchanged since" and, if that message is far back, re-injects the relevant span near the end instead of re-running the read. Stale copies are collapsed so only one live version exists.

## Ten live rules stated last beat a long system prompt

Prompt-side levers rank below the mechanical ones because their measured effects are averages, not guarantees. Within those limits, the evidence points one way. IFScale shows llama-4-scout, a MoE with about 17B active parameters, at **100% adherence with 10 instructions but 54.4% at 50**. Small models mostly *omit* instructions rather than half-follow them ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)). AgentIF finds compliance falling sharply past about 3,000 tokens and 40 constraints, with tool specifications among the hardest categories ([arXiv 2505.16944](https://arxiv.org/html/2505.16944v1)). Laban et al. attribute a 39% multi-turn drop mostly to "a significant increase in unreliability", not lost aptitude ([arXiv 2505.06120](https://arxiv.org/abs/2505.06120)). Taken together, the rule a stubborn model breaks is usually already in its prompt, and it loses to recent context. Three changes follow. Keep the always-on rule set near ten items and inject stage-specific rules per turn, which suits dynamic agent-instruction injection. State the one binding constraint at the end of the latest turn, next to the decision. Offer a compact prompt variant, as Cline does: its "Compact Prompt" is about 90% smaller, and Cline says most models under 30B fail with its full prompt ([Cline docs](https://docs.cline.bot/running-models-locally)). Verbatim prompt repetition is the best-measured cheap trick, with 47 wins and 0 losses for non-reasoning models. Under reasoning it was neutral, at 5 wins, 1 loss and 22 ties ([arXiv 2512.14982](https://arxiv.org/html/2512.14982v1)), so for an always-thinking model, repeating only the binding rule is the variant worth probing. On phrasing, naming the forbidden thing in "do not call X" primes X ([arXiv 2601.08070](https://arxiv.org/html/2601.08070v1)), and open models broke prohibitions more often under negated prompts ([arXiv 2601.21433](https://arxiv.org/pdf/2601.21433)). A refusal should therefore say what the next reply must be, for example "the next reply is one read_file call with path P", without echoing the refused shell line. That rests on narrow studies and has not been tested in agent loops. LFM2.5's own card points the same way: for an agent harness it suggests enabling tool-use enforcement ([LFM2.5 card](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B)), which concedes that wording alone does not hold.

## Fine-tuning on the harness's own refusals is the durable fix, at a price

When decoding and harness levers plateau, the remaining lever is the weights. FISSION-GRPO targets exactly "repetitive invalid re-calls after a tool error". It turns each failed trajectory into a training instance and resamples recovery rollouts, lifting Qwen3-8B on BFCL v4 multi-turn from 42.75% to 46.75%, with error recovery up 5.7 points ([arXiv 2601.15625](https://arxiv.org/pdf/2601.15625)). Learning-from-failure shows that failed trajectories, labelled as such, improve agent tuning ([arXiv 2402.11651](https://arxiv.org/abs/2402.11651v2)). FireAct reports large gains from just 500 trajectories on a 7B model ([arXiv 2310.05915](https://arxiv.org/abs/2310.05915v1)), but a 70B replication with 162 examples fell below few-shot prompting ([arXiv 2401.14016](https://arxiv.org/pdf/2401.14016)), so small datasets are not a sure win. Liquid officially supports TRL SFT-LoRA, DPO-LoRA and GRPO-LoRA for LFM2.5 and publishes a base checkpoint ([LFM2.5 card](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B)). The harness already logs everything such a dataset needs. Each repeated refused call, prose answer and redundant read is a "rejected" sample, and the harness's correction is the "chosen" one. The cost is real. Unsloth now advises against 4-bit QLoRA for MoE and recommends bf16 LoRA ([Unsloth](https://unsloth.ai/docs/models/qwen3.5/fine-tune.md)). At 24B total parameters that means about 48 GB of weights before activations, which is arithmetic from the parameter count rather than a measurement. A fine-tuned checkpoint is also a model change that only the owner can make.

Quantization is unlikely to be the main cause. W8A8 and W4A16 are about lossless for reasoning models, and quantized models "do not exhibit increased output lengths" ([arXiv 2504.04823](https://arxiv.org/abs/2504.04823)). The KV cache deserves a check, though. llama.cpp warns that extreme KV quantization such as `-ctk q4_0` "can substantially degrade the model's tool calling performance" ([function-calling.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)), and 6-bit KV quantization collapsed IFEval for Qwen-2.5-7B ([arXiv 2606.09864](https://arxiv.org/pdf/2606.09864)). The harness should read and record the server's cache type and report it, not change it. The least-supported item is a second model acting as judge or shim. Goose's tool shim and Gemini CLI's 0.9-confidence loop judge ship without published success rates ([Goose](https://goose-docs.ai/docs/guides/tool-shim)), and CRITICTOOL finds weak self-critique across most models ([arXiv 2506.13977](https://arxiv.org/abs/2506.13977)). A deterministic rewriter beats both for patterns this regular.

## A per-model profile chosen by five probes keeps the code generic

Every lever above reduces to data, so model-specific code is unnecessary. The profile holds two kinds of field. Detected fields are read from the server: the tool handler and template (`/props`, and the "Chat format" log line), the think-open token id (`/tokenize`), whether tool arguments are schema-checked, the KV cache type, and whether the server honours a reasoning budget. Measured fields are chosen by a fixed probe battery, one scripted scenario per failure mode, each run several times per candidate setting. A refused shell line measures the repeat rate after refusal. A spiral-prone prompt measures the reasoning-token distribution and the termination rate. A turn that requires a structured answer measures the prose rate and the schema-violation rate. A file already in context measures the redundant-read rate. A truncated-reasoning continuation measures the `<think>` re-open rate.

| Profile field | Candidates the probes choose between |
|---|---|
| `reasoning_cap`, `max_tokens` | e.g. 4k / 8k / 16k reasoning; the answer allowance on top |
| `cut_message` | one-line answer-now sentence; none |
| `think_ban` | `logit_bias` ban plus stop; stop only; no-reasoning user turn |
| `tool_choice_mode` | string `required` with one tool; `required` with a reduced set; `auto` plus extraction pass |
| `structured_path` | `response_format` with no tools; tool call plus validation |
| `history_policy` | drop corrected refusals; collapse to one line; keep |
| `refusal_role` | tool message; tool message plus a user-role restatement |
| `nudge_at`, `reset_at` | 2/3, 3/4, 4/5 |
| `prompt_variant` | full; compact; binding rule repeated last |
| `sampling` | temperature 0.1 / 0.6 / 0.8; DRY off / 0.8-1.75-2 / 0.8-1.75-4 with a 1024 window |

A setting is adopted only if it lowers its probe's failure rate without lowering the hidden-test score of a full run, which fits a Measure/Fix discipline. A model with a JSON-style tool handler and a well-behaved budget ends up with a lighter profile than LFM2.5, using the same code.

## Conclusion

The research changes the diagnosis more than the remedy. These five failures look like one stubborn model ignoring instructions. The sources point instead to two separate causes. Three of the failures are permitted by the decoder configuration, and llama.cpp quietly weakens the configuration the harness thinks it is sending. The other two are reinforced by the harness's own transcript, through self-conditioning on refused calls and through stale duplicate reads. Neither cause responds well to stronger wording, which is why the top of the ranking is entirely mechanical. A second implication: the best-measured techniques (constrained decoding, DRY, context pruning) were measured on dense 1-70B models. The specific claims about LFM2.5 here, how much a cap costs it, whether the `<think>` ban composes with a forced grammar, and whether a user-role refusal outweighs a tool-role one, are untested. That is why the profile must be filled by measurement rather than copied from this report.

The largest unknown in the stack is the wording of refusals. It is the most-discussed lever in practice, yet no source ablates it for small models, and the 90.5%-to-57.2% drop after one failure says it is where the most outcome is decided. A harness that returns the exact corrected call, runs or rewrites a shell-composed line deterministically, and erases the refused attempt afterwards tests the one hypothesis the literature most strongly implies and has not yet measured. Its own refusal logs then become the DPO dataset if the weights ever need to change.
